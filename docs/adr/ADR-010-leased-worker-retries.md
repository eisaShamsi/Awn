# ADR-010: حجز العامل وإعادة المحاولة المحدودة

- **الحالة:** مقبول
- **التاريخ:** 2026-08-23

## السياق

استهلاك الموافقة وتشغيل الأداة داخل مهمة خلفية لعملية API لا يكفي وحده؛ فقد تتوقف العملية بعد تسجيل الموافقة أو أثناء الأثر. كما قد يعمل أكثر من عامل، ولا يجوز لعامل انتهت مهلة حجزه أن يسجل نتيجة فوق عامل استعاد العمل.

## القرار

- تستهلك الموافقة المطابقة وتُنشأ استدعاءات الأدوات بحالة `pending` داخل معاملة واحدة؛ ولا تُشغّل الأداة داخل تلك المعاملة.
- يستخدم عامل مستقل PostgreSQL كطابور. يحجز صفًا متاحًا بقفل قصير و`SKIP LOCKED`، ويسجل `lease_owner` و`lease_expires_at` ثم يغلق المعاملة قبل استدعاء الأداة.
- لا يقبل حفظ النجاح أو الفشل إلا من العامل الذي ما زال يملك الحجز المسجل.
- يستطيع عامل آخر استعادة حجز منتهي. لا تعد الاستعادة محاولة جديدة، لأن الانقطاع قد يقع بعد الأثر وقبل حفظ النتيجة، ولذلك لا تُشغّل في هذا المسار إلا أداة تدعم منع التكرار.
- تصنف أخطاء المهلة والاتصال والأخطاء المعلنة مؤقتة على أنها قابلة لإعادة المحاولة. الحد الافتراضي ثلاث محاولات بتراجع زمني أسي محدود؛ أما أخطاء المخطط والسياسة والمسار والملف الموجود المختلف فهي نهائية.
- يوفر `apps.worker.main` عملية عامل مستمرة. ويمكن لعملية API تشغيل دورة قصيرة بأفضل جهد بعد الموافقة لتقليل زمن الانتظار محليًا؛ ويظل السجل الدائم هو مصدر الحقيقة والاستعادة.

## النتائج

- ينجو العمل المدرج من إعادة تشغيل API أو العامل، ولا تعتمد صحته على ذاكرة عملية واحدة.
- تمنع ملكية الحجز عاملًا متأخرًا من تزوير حالة نهائية بعد انتقال العمل.
- تحتاج الأدوات ذات الأثر إلى سلوك منع تكرار حقيقي واختبار انقطاع، لا إلى مفتاح محفوظ فقط.
- يبقى إلغاء تشغيل قيد التنفيذ وسجل الأحداث التراكمي عملين منفصلين في المرحلة الثانية.
