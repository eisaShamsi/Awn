# تصميم FC-002: الإلغاء الآمن للتنفيذ الجاري

- **الحالة:** `APPROVED_FOR_BUILD`
- **المرحلة:** `DESIGN`
- **المفهوم الحاكم:** `FC-002 v0.3`
- **بصمة المفهوم المعتمد:** `b3431cb639070949deb06286497240ebfdf350c651795841b524a233c3fb2bdf`
- **دليل اعتماد المالك:** «أعتمد FC-002 v0.3» بتاريخ 2026-08-24

## 1. الهدف والحد

يحوّل التصميم طلب الإلغاء إلى **أمر دائم مرتب مقابل حد الالتزام بالأثر**. إنشاء الأمر لا يعني أن الأداة توقفت؛ بل يمنع كل أثر لم يُلتزم ببدئه، ويوقف الاستعادة وإعادة المحاولة، ثم يصالح النتيجة الحقيقية للأثر الجاري أو المتأخر.

لا يضيف التصميم قتلًا قسريًا للعملية، ولا تراجعًا تلقائيًا عن أثر مكتمل، ولا سجل تدقيق عام. أدوات عَوْن الحالية (`tasks.create` و`files.create`) عمليات ذرية قصيرة ولا تعلن نقطة توقف وسطية آمنة؛ لذلك يمكن منعهما قبل حد بدء الأثر، أما بعده فتُعرض الحقيقة بوصفها مكتملة أو جزئية أو غير مؤكدة وفق الدليل.

## 2. قرارات التصميم

### 2.1 أمر إلغاء مستقل عن النتيجة

يضاف كيان دائم `RunCancellation` واحد لكل تشغيل:

- `id`, `run_id`, `requested_by`.
- `status`: `accepted | uncertain | cancelled | partially_succeeded | completed | execution_failed`.
- `reason_code` من قائمة مغلقة ومنقحة.
- `received_at`, `requested_at`, `resolved_at`, `updated_at`.

وجود السجل بحالة `accepted` هو حد **قبول الإلغاء**. لا تنشئ الطلبات غير المخولة أو غير القابلة للإلغاء سجلًا، وتعيد API نتيجة صريحة بدل إظهار قبول زائف. يمنع القيد الفريد على `run_id` تكرار أمر الإلغاء.

### 2.2 دليل إلغاء تراكمي ومحدود

يضاف `RunCancellationEvent` تراكمي لا يُعدّل بعد الإدراج:

- `id`, `cancellation_id`, `tool_call_id` الاختياري.
- `event_type` من قائمة سماح: قبول الأمر، منع استدعاء قبل الأثر، عبور حد الالتزام، إلغاء بلا أثر، أثر جزئي، أثر مكتمل، نتيجة غير مؤكدة، دليل متأخر، وتعارض دليل.
- `source_type`: `owner_action | cancellation_api | current_worker | reconciliation_worker | database_verification`.
- `evidence_code` تقني موجز، و`evidence_fingerprint` اختياري للمعلومة المتحققة،
  و`related_evidence_fingerprint` اختياري لربط طرفي التعارض.
- `superseded_status` اختياري من قائمة الحالات المغلقة عند فتح مصالحة بسبب تعارض صحيح.
- `occurred_at` الاختياري لوقت وقوع الواقعة كما أثبتها المصدر، و`observed_at` الإلزامي من ساعة الخادم لوقت إدخالها.

لا يحفظ الحدث مدخل الأداة أو ناتجها أو سببًا حرًا من المستخدم. تبقى النتيجة الفعلية المنقحة في `tool_calls.output` وفق عقد الأداة، بينما تحفظ الأحداث ترتيب الحقائق فقط.

### 2.3 حد الالتزام بالأثر

يضاف `effect_committed_at` و`effect_commit_token` إلى `tool_calls`. لا تعني العلامة أن
الأثر وقع؛ بل تعني أن العامل عبر نقطة التحكم الأخيرة وأصبح التنفيذ التالي محتملًا. يصبح
مسار العامل:

1. يحجز الاستدعاء زمنيًا؛ الحجز وحده لا يعني بدء الأثر.
2. يتحقق من سجل الأداة والسياسة والمدخلات.
3. ينفذ معاملة قصيرة `commit_effect` تقفل التشغيل ثم الاستدعاء بالترتيب نفسه في كل الكتابات.
4. إذا وجد أمر إلغاء، يلغي الاستدعاء قبل الأثر ولا يشغل handler.
5. إن لم يوجد، يثبت `effect_committed_at` ورمز التزام عشوائيًا ثم يستدعي الأداة، من دون تمرير الرمز إلى handler.

هذا الحد هو مرجع السباق: أمر الإلغاء الذي يثبت أولًا يمنع الأثر؛ وحد الالتزام الذي يثبت
أولًا يجعل نتيجة الأداة غير قابلة للادعاء بأنها توقفت حتى يصل دليل. التعطل بعد commit الحد
وقبل handler لا يثبت وقوع أثر، بل يقود إلى `uncertain` ما لم يثبت لاحقًا «لا أثر» أو أثر
فعلي. تغطي اختبارات حقن الأعطال ما قبل الحد، وما بعده قبل handler، وما بعد الأثر قبل حفظ
الناتج، والإلغاء في كل نافذة.

### 2.4 حالات التشغيل والاستدعاء

تضاف حالتان غير نهائيتين إلى `RunStatus`:

- `cancellation_requested`: قُبل الأمر، ويجري منع المتبقي أو انتظار دليل الجاري.
- `cancellation_uncertain`: انتهت مهلة العامل أو تعذر إثبات نتيجة أثر بدأ؛ لا توجد إعادة محاولة تلقائية.

وتضاف `outcome_unknown` إلى `ToolCallStatus` و`PlanStepStatus`. يسمح الدليل المتحقق اللاحق بنقل الحالة غير المؤكدة إلى الحقيقة النهائية من دون بدء تنفيذ جديد.

تبقى `cancelled` نهائية ومحصورة في ثبوت عدم وقوع أثر. تبقى `partially_succeeded` و`succeeded` حقائق أثر، ولو وصل الدليل بعد طلب الإلغاء.

تصنف الحالات من زاويتين: `outcome_unknown` **مغلقة أمام الجدولة وإعادة المحاولة** لكنها
مفتوحة للمصالحة فقط؛ أما `pending` و`executing` فهما قابلتان للجدولة قبل قبول الإلغاء.
تظل `cancellation_requested` و`cancellation_uncertain` غير نهائيتين ويكون
`completed_at = null`؛ وتضبط الحالات النهائية وحدها `completed_at`.

| Run `cancellation_uncertain` | `cancelled`, `partially_succeeded`, `succeeded`, `failed` | غير نهائية؛ دليل غير متعارض متحقق أو تدخل المالك فقط |
| Run `cancelled/partially_succeeded/succeeded/failed` بعد أمر إلغاء | `cancellation_uncertain` عند دليل صحيح متعارض فقط | يصفّر `completed_at` ولا يعيد فتح الجدولة؛ تحفظ النهاية السابقة في الحدث |

| Cancellation `cancelled/partially_succeeded/completed/execution_failed` | `uncertain` عند دليل صحيح متعارض فقط | يصفّر `resolved_at` ويحفظ القرار السابق تراكميًا |

تظل انتقالات التشغيل السابقة لـFC-002 كما هي، ولا يعاد فتح تشغيل نهائي عند طلب متأخر؛
يعيد API `too_late`. لا يغيّر دليل مكرر الحالة. لا يمحو دليل متعارض النهاية السابقة ولا
يستبدلها بأحدث ادعاء، لكنه يسحب صفة اليقين منها وينقل العرض والكيانات المرتبطة إلى مسار
المصالحة غير المؤثر أعلاه.

### 2.6 ترتيب الأقفال

كل كتابة تمس الطابور أو الإلغاء تتبع ترتيبًا واحدًا:

1. `runs`.
2. `tool_calls` مرتبة بالمعرف.
3. `run_cancellations`.
4. `plan_steps`.

يعدّل حجز PostgreSQL ليستبعد التشغيلات التي تحمل أمر إلغاء، مع الحفاظ على `SKIP LOCKED`.
تستخدم عمليات claim/commit/result/cancel نفس الترتيب ولا تقفل call قبل run. يستخدم SQLite
المسار المنطقي نفسه من دون ادعاء اختبار التزامن الحقيقي. يختبر السباق الفعلي على PostgreSQL.

### 2.7 مصفوفة السلطة وحدود الثقة

| الممثل | POST/GET الإلغاء | قراءة الأمر | إدراج دليل أثر | حسم الحالة |
|---|---|---|---|---|
| المالك داخل مساحة التشغيل | نعم، بفعل مباشر | نعم | لا | لا |
| مستخدم/مساحة أخرى | `404` | لا | لا | لا |
| BFF | ينقل فعل المالك فقط ولا ينشئه | يعرض المنقح | لا | لا |
| النموذج/الأداة/المحتوى الخارجي | لا | لا | لا | لا |
| العامل الحالي | لا ينشئ أمرًا | نعم للتحكم | لالتزامه الأصلي فقط | لا؛ يقدم دليلًا للخدمة الحتمية |
| عامل مصالحة | لا | نعم | دليل قراءة غير مؤثر ومربوط بالنداء | لا؛ يقدم دليلًا للخدمة الحتمية |
| خدمة المصالحة الحتمية | لا | نعم | تتحقق وتدرج حدثًا | نعم وفق جدول القرار فقط |

لا يوجد مسار API عام للدليل المتأخر. يقبل المسار الداخلي الدليل فقط إذا تطابقت هوية
`tool_call_id` و`run_id` و`idempotency_key` وبصمة المدخل الثابت و`effect_commit_token`
ومخطط ناتج الأداة ومصدر السماح. يبصم الناتج المنقح بعد التحقق. الدليل المكرر ذو البصمة
نفسها idempotent؛ والدليل المخالف للنطاق أو المخطط يرفض. لا يمنح هذا الإصدار مصدرًا صحيحًا
أسبقية لمجرد أنه وصل أخيرًا: إذا أكد دليلان متحققان حقيقتين متنافيتين، يسجل
`evidence_conflict` مع الحالة السابقة وبصمتي الدليل، وينقل call/step إلى `outcome_unknown`
والتشغيل والإلغاء إلى `cancellation_uncertain/uncertain` حتى لو كانت الحالة السابقة نهائية.
لا يمحو السجل السابق ولا يفتح claim أو handler. لا يحسم التعارض آليًا إلا عقد تحقق خاص
بالأداة يثبت حقيقة حصرية؛ وإلا يبقى ظاهرًا حتى تدخل مالك موثق في قدرة لاحقة.

## 3. عقد API

تضاف المسارات المقيدة بالمالك ومساحة العمل والمحادثة والتشغيل:

- `POST .../runs/{run_id}/cancellation`
- `GET .../runs/{run_id}/cancellation`

لا يقبل `POST` نصًا حرًا أو مدخلًا من النموذج. يعيد `CancellationRequestResult`:

- `decision`: `accepted | already_requested | too_late | not_cancellable`.
- `received_at` بساعة API، لتمييز استلام الخادم عن تثبيت الأمر.
- `run_status` الفعلي.
- `cancellation` عند وجود أمر دائم، متضمنًا أحداث الدليل المنقحة.

لا تعيد الاستجابة `accepted` إلا بعد commit. الطلب المكرر يعيد السجل نفسه، والتشغيل النهائي يعيد `too_late` من دون تغيير تاريخه، والحالة السابقة للتنفيذ تعيد `not_cancellable`. المورد خارج النطاق يعيد `404` ولا يكشف وجوده.

## 4. معاملة قبول الإلغاء

داخل معاملة واحدة:

1. يتحقق النطاق ويقفل التشغيل ثم استدعاءاته.
2. يعيد السجل الموجود للطلب المكرر.
3. يقبل فقط تشغيلًا في `executing`؛ الحالات النهائية متأخرة، وانتظار الموافقة يستخدم مسار الرفض الحالي.
4. ينشئ أمر الإلغاء والحدث الأول.
5. يلغي كل `pending`، وكل `executing` لم يثبت `effect_committed_at`، ويصفر حجزه ويمنع محاولاته التالية.
6. إذا لم يبق أثر جارٍ: يحسم إلى `cancelled` إن لم يقع أثر، أو `partially_succeeded` إذا نجح بعضه وتوقف الباقي.
7. إذا بقي أثر بدأ: ينقل التشغيل إلى `cancellation_requested` ويبقي ملكية العامل اللازمة لاستقبال الدليل.

لا تستدعي المعاملة أداة ولا تنتظر شبكة أو عاملًا، ولذلك يبقى إقرارها المحلي ضمن هدف الثانيتين في الظروف المعتادة.

## 5. مصالحة نتيجة العامل

| حقيقة الاستدعاءات بعد قبول الأمر | حالة الإلغاء | حالة التشغيل | الرسالة للمستخدم |
|---|---|---|---|
| كلها `cancelled` قبل الأثر | `cancelled` | `cancelled` | أُلغي قبل وقوع أثر |
| بعضها `succeeded` والباقي `cancelled` | `partially_succeeded` | `partially_succeeded` | وقع أثر جزئي وتوقف الباقي |
| كلها `succeeded` | `completed` | `succeeded` | اكتمل الأثر؛ كان الإلغاء متأخرًا أو تعذر إيقاف الجاري |
| أثر بدأ ثم انتهت المهلة أو عاد فشل غير حاسم | `uncertain` | `cancellation_uncertain` | تعذر تأكيد التوقف؛ يعرض آخر دليل وتوقيته |
| لا أثر ناجح، ويوجد فشل حاسم لا ينتسب إلى منع الإلغاء | `execution_failed` | `failed` | توقف التنفيذ بسبب فشل؛ لا أثر مثبت |

يطبق reducer ترتيب الأولوية التالي على استدعاءات الأدوات، مرة واحدة وبنتيجة وحيدة:

1. أي `evidence_conflict` مفتوح أو `outcome_unknown` يجعل `uncertain/cancellation_uncertain`، ولو كانت الحالة السابقة نهائية أو نجح call آخر.
2. وجود call ملتزم ما زال تحت lease صحيح يبقي `accepted/cancellation_requested`.
3. انتهاء lease بعد commit بلا دليل يجعل `uncertain/cancellation_uncertain`.
4. بعد زوال المجهول: وجود `succeeded` مع أي `failed/cancelled` يجعل النتيجة جزئية.
5. كون جميع calls `succeeded` يجعل `completed/succeeded`.
6. عدم وجود أثر ناجح مع أي `failed` يجعل `execution_failed/failed`.
7. كون البقية `cancelled` فقط، مع ثبوت عدم الأثر، يجعل `cancelled/cancelled`.

الحالات `skipped` غير المؤثرة تحفظ لكنها لا تدخل حساب حقيقة الأثر. بعد قبول الإلغاء لا
يتحول فشل مؤقت إلى إعادة محاولة. تستدعي دورة العامل مصالحة غير مؤثرة للاستدعاءات ذات
الحجز المنتهي. إذا وصل لاحقًا دليل مطابق لعقد §2.7، يسجل `late_effect_evidence` ويحدث
الحقيقة من `uncertain` وفق الترتيب نفسه؛ ولا يعد ذلك إذنًا بتنفيذ جديد. يسمح
`outcome_unknown → cancelled` فقط عندما يثبت دليل لاحق أن الإلغاء سبق الأثر؛ أما الفشل
الحاسم النهائي فلا يعاد توصيفه.

## 6. واجهة المستخدم

تعرض منطقة **التشغيلات النشطة** كل تشغيل غير نهائي في المحادثة، بهوية ثابتة تتضمن وقت
البدء ومعرفًا مختصرًا وحالته. يرتبط زر **«إلغاء التنفيذ»** وبطاقة الإلغاء صراحةً بـ`run_id`،
ويظهر الزر داخل صف كل تشغيل `executing` لا يحمل أمرًا. يستطيع المالك اختيار أي تشغيل لعرض
تفاصيله، ولا تستخدم الواجهة «الأحدث» بديلًا عن الاختيار. الزر أصلي يمكن بلوحة المفاتيح،
ولا يطلب تأكيدًا ثانيًا لأن المقصود فرامل عاجلة ولا ينشئ أثرًا جديدًا.

تحتفظ الواجهة بخريطة cancellation keyed by `run_id`، وتزامن `GET cancellation` لكل تشغيل
نشط وللتشغيل المحدد عند فتح المحادثة وتغييرها وإعادة الاتصال، وفي دورة التحديث الحالية كل
2.5 ثانية. تستمر الدورة خلال `accepted` و`uncertain`، وتحفظ بطاقة عدم اليقين ظاهرة حتى
دليل لاحق. تعلن الواجهة تغير حالة التشغيل المعني فقط، لا كل poll، ويذكر الاسم الميسّر
للبطاقة والزر معرف التشغيل/وقته كي لا يلتبس الإعلان عند تعدد التشغيلات.

بعد الضغط:

- تعرض محليًا «جارٍ إرسال طلب الإلغاء»؛ لا تدعي هذه الحالة استلام الخادم.
- يعطل الزر أثناء الطلب.
- تعرض استجابة `accepted` نص «قُبل طلب الإلغاء؛ يجري التحقق من التوقف»، لا «أُلغي».
- تظهر بطاقة حالة مستقلة ذات `role="status"` و`aria-live="polite"`، بدل جعل سجل المحادثة كاملًا منطقة حية.
- تستخدم الحالات نصًا ورمزًا إضافة إلى اللون، وتحافظ على العربية وRTL وCalibri.
- يعرض خط زمني داخل البطاقة `received_at` بوصفه «استلم عَوْن الطلب»، ثم `requested_at`
  بوصفه «ثُبّت أمر الإلغاء»؛ لا تستخدم أي منهما شارة نجاح نهائي.
- ترتب البطاقة: النتيجة الحالية، ثم معنى الحالة، فالخطوة الآمنة التالية، ثم آخر دليل وتوقيته.
- تعيد `already_requested` السجل نفسه وتستأنف مراقبته، وتعيد `too_late` و`not_cancellable`
  رسالة صادقة ولا تغير شارة التشغيل.
- إذا فُقدت استجابة POST، تنفذ GET: إن وجد السجل تعرضه؛ وإن أعاد `404` تعرض «لم يتأكد
  قبول الإلغاء» وتعيد تمكين الزر؛ وإن تعذر GET أيضًا تعرض «تعذر التحقق» وتتيح إعادة POST
  الآمنة. ينتقل التركيز إلى البطاقة بعد القبول، وإلى رسالة الخطأ ثم زر إعادة المحاولة عند
  الفشل. لا يعني `404` خارج النطاق أن المورد موجود.

| الحالة | النص/الرمز | النبرة/اللون الدلالي | الخطوة الآمنة التالية |
|---|---|---|---|
| إرسال محلي | `↗` جارٍ إرسال الطلب | محايد | الانتظار؛ لا ادعاء استلام |
| استلام الخادم | `↓` استلم عَوْن الطلب | معلوماتي | انتظار قرار التثبيت |
| أمر مقبول/تحقق جارٍ | `⏸` قُبل الطلب؛ يجري التحقق | تحذير هادئ، لا علامة نجاح | لا تبدأ تشغيلًا بديلًا |
| تعذر/رفض/تأخر | `!` لم يصبح الطلب أمرًا حاكمًا | خطر أو تحذير | راجع الحالة الفعلية؛ أعد المحاولة فقط إذا أتيح |
| لا أثر | `■` أُلغي قبل الأثر | نجاح تحكم، لا نجاح أثر | لا إجراء لازم |
| أثر جزئي | `◐` وقع أثر جزئي وتوقف الباقي | تحذير | راجع الأثر المثبت؛ لا تعويض تلقائي |
| أثر كامل | `↦` اكتمل الأثر وكان الإلغاء متأخرًا | معلوماتي صريح، لا احتفال | راجع النتيجة؛ التعويض غير متاح تلقائيًا |
| غير مؤكد | `?` تعذر تأكيد التوقف | تحذير مرتفع | لا تعاود التنفيذ؛ راجع آخر دليل أو المورد |
| دليل متعارض | `⇄` تعارض دليل النتيجة؛ المصالحة مطلوبة | تحذير مرتفع | لا تعاود التنفيذ؛ قارن آخر دليلين وتوقيتهما |
| فشل تنفيذ بلا أثر مثبت | `×` توقف بسبب فشل | خطر | راجع الخطأ؛ لا تفترض أن الإلغاء سببه |

يحظر رمز الحذف أو السلة أو الممحاة، ويحظر check أخضر عند مجرد الاستلام أو القبول. تبقى
كل حالة مفهومة من النص والرمز من دون اللون. تلتف العربية الطويلة بلا اقتطاع، وتتحول
البطاقة في العرض الضيق إلى عمود يحفظ النتيجة والخطوة التالية قبل التفاصيل، وتعرض المعرفات
والأكواد المختلطة داخل `bdi dir="ltr"`. في حالة التعارض تعرض التفاصيل النهاية السابقة
وآخر دليلين وتوقيتهما من دون أسرار. تبقى Calibri أول خط في السلسلة.

## 7. ضوابط السلامة

- تحقق المالك والمساحة والمحادثة والخادم في كل POST وGET.
- لا يملك المحتوى الخارجي أو رسالة النموذج مسارًا لإصدار الإلغاء؛ المسار فعل مستخدم مباشر عبر BFF المحلي.
- لا مدخل حر ولا أسرار في سجل الإلغاء، والأحداث بقائمة أنواع وأكواد مغلقة.
- يبقى `effect_commit_token` داخليًا بين المستودع والعامل ولا يظهر في API أو الأحداث أو السجلات.
- أمر الإلغاء يمنع claim والاستعادة وإعادة المحاولة قبل أي قرار نموذج.
- لا تمسح نتيجة أداة حقيقية، ولا تسمح النتيجة المتأخرة بكتابة مدخل جديد أو توسيع الصلاحية.
- لا تعويض تلقائي؛ أي تعويض مستقبلي وظيفة وأثر مستقلان يحتاجان مفهومًا وصلاحية مناسبين.

### 7.1 دورة الحياة والحذف والتصدير

يصنف أمر الإلغاء وأحداثه «حالة تشغيل»، فيرثان عمر التشغيل ومساحة العمل ويصدران معها
ويحذفان بحذفها وفق سياسة نموذج التهديد. تستخدم المفاتيح `ON DELETE CASCADE` من run إلى
cancellation ومن cancellation إلى events، ولا تبقى أحداث يتيمة. لا تنقل هذه الأحداث إلى
احتفاظ سجل التدقيق العام ذي 90 يومًا. يبقى `tool_calls.output` وفق عقد التنقيح والاحتفاظ
القائم، ولا تنسخه الأحداث.

### 7.2 فرق نموذج التهديد

| التهديد | أثر FC-002 والضابط | الخطر المتبقي |
|---|---|---|
| `T-03` تبديل السلطة/المدخل | فعل مالك مباشر، نطاق 404، ومدخل وبصمة ثابتان | المصادقة/CSRF لازمان قبل نشر شبكي |
| `T-04` تكرار الأثر | أمر دائم، commit token، منع claim/retry، ومصالحة idempotent | المزود الخارجي المستقبلي يحتاج تحقق نتيجة خاصًا به |
| `T-06` خلط المساحات | كل POST/GET ودليل داخلي مقيد بالمالك/run/workspace/call | دفاع صفوف إضافي عند تعدد المستخدمين |
| `T-07` نجاح زائف | حالات لا أثر/جزئي/كامل/مجهول وجدول reducer | الأدوات الحالية لا تقدم توقفًا تعاونيًا بعد commit |
| `T-08` عبث الدليل | أحداث تراكمية، مصدر مغلق، بصمة دليل، ومنع overwrite | سجل التدقيق العام المترابط ما زال وظيفة لاحقة |

## 8. الترحيل والرجوع

يضيف ترحيل Alembic واحدًا:

- جدولي `run_cancellations` و`run_cancellation_events`.
- `tool_calls.effect_committed_at` و`effect_commit_token`.
- قيم الحالات الجديدة في قيود `runs` و`plan_steps` و`tool_calls`.

لا يغير بيانات تاريخية ولا ينشئ أوامر إلغاء لها. يعيد downgrade القيود والأعمدة والجداول فقط بعد التحقق من عدم وجود حالات جديدة غير قابلة للتمثيل؛ يستخدم ترتيب إسقاط آمنًا للقيود والمفاتيح.

## 9. مصفوفة التتبع والاختبار

| معيار المفهوم | عناصر التصميم | دليل الاختبار المطلوب |
|---|---|---|
| `AC-001` | النطاق، القيد الفريد، قرارات API الأربع | طلب صحيح ومكرر، مساحة خاطئة، تشغيل نهائي، وحالة غير قابلة للإلغاء |
| `AC-002` | commit قبل `accepted` وحد الالتزام | بقاء الأمر بعد restart، وترتيب الأمر/الحد، وقياس POST أقل من ثانيتين على API/PostgreSQL محليين مع handler محجوب لإثبات أنه لا ينتظر العامل |
| `AC-003` | إلغاء pending وpre-effect ومنع claim | صفر handler وصفر أثر وصفر retry بعد الإلغاء |
| `AC-004` | `commit_effect`، ترتيب الأقفال، منع retry | سباق claim/cancel وcommit/cancel وcomplete/cancel وحقن أعطال النوافذ الأربع على PostgreSQL |
| `AC-005` | جدول الانتقالات وreducer الكلي | decision table لكل مزيج مسموح، ومنها failed/skipped/mixed/conflict؛ و`cancelled` لثبوت لا أثر فقط |
| `AC-006` | الديمومة، الأحداث، uncertain، عقد late evidence | restart، انتهاء lease، منع stale overwrite، ودليل مطابق/مكرر/متعارض بعد كل نهاية؛ يسحب التعارض اليقين ولا يمحو التاريخ |
| `AC-007` | تشغيلات keyed by run، مزامنة GET، خط زمني، بطاقة وتركيز ومصفوفة بصرية | E2E بتشغيلين نشطين وإلغاء كل منهما منفردًا، والتحميل/reconnect وكل انتقال/conflict وفشل نقل، مع الوصول وRTL/Calibri |
| `AC-008` | مصفوفة السلطة، لا body حر، أكواد مغلقة، lifecycle | canary، cross-workspace، عامل/token/input خاطئ، schema فاشل، duplicate/forged/verified conflict، cascade/export، وفحص الاستجابات والسجلات |

تستمر بوابات المشروع الكاملة: Ruff، pytest مع PostgreSQL، Alembic upgrade/check/downgrade، npm audit، lint، typecheck، build، وفحص متصفح حي.

## 10. حدود معلنة

- لا توجد أداة حالية تعلن توقفًا تعاونيًا داخل أثر بدأ؛ ولذلك لا يوعد المستخدم بوقف `tasks.create` أو `files.create` بعد `effect_committed_at`.
- لا يقرر هذا التصميم كيف يعوض أثرًا وقع.
- لا يحل هذا السجل المحدود محل سجل التدقيق العام المطلوب لاحقًا في المرحلة الثانية.
